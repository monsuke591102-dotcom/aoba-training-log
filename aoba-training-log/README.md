# AOBA TRAINING LOG

中学生の野球選手向けの自主練習管理アプリです。練習メニュー・記録・目標と履歴、予定・休養日・振り返りは、開いたブラウザーの IndexedDB に保存します。配信元やブラウザープロファイルを変えると保存先も変わります。

## Windows で起動

Node.js 24.22.1 と pnpm 11.25.0（動作確認済み）を用意し、このフォルダで PowerShell を開きます。

```powershell
pnpm.cmd install --frozen-lockfile
pnpm.cmd dev
```

PowerShell に表示された Local URL をブラウザーで開きます。

```powershell
pnpm.cmd test
pnpm.cmd build
```

GitHub Pages のようにサブパスで配信する場合は、ビルド時にリポジトリ名を指定します。

```powershell
$env:VITE_BASE_PATH = "/aoba-training-log/"
pnpm.cmd build
```

## iPhoneでの試合記録の隔離検証

配信にはNetlifyなどで作成した専用の静的HTTPSサイトを使います。本番と異なるホスト名を先に確定し、リポジトリやSupabaseをサイトに連携させず、検証用のビルド成果物だけをサイトのルートに配置します。配信先が未確定の間は次の例でローカルビルドだけを確認できます。`invalid` はiPhoneで接続するためのURLではありません。

```powershell
$env:VITE_MATCH_TEST_ORIGIN = 'https://aoba-match-test.invalid'
$env:VITE_MATCH_TEST_BUILD = '4L8-test-01'
pnpm.cmd exec vite build --mode match-test --outDir dist/match-test
```

- 実際の配信時は、承認後に `VITE_MATCH_TEST_ORIGIN` を確定したHTTPSオリジンに置き換えます。末尾スラッシュやパスは付けません。配信するのは `dist/match-test` の中身だけです。通常のPagesビルドは従来のコマンドを使用します。
- Codespacesを使う場合は、ポート一覧の4173の転送先URLを `VITE_MATCH_TEST_ORIGIN` に設定し、ビルドとプレビューの両方を `--mode match-test` で起動します。プレビューには `--host 0.0.0.0 --port 4173 --strictPort` を指定します。ポートは非公開のまま、CodespaceにアクセスできるGitHubアカウントの通常のブラウザーで転送先URLを開きます。過去の記録を使う場合は同じ転送先オリジンを維持します。
- 旧ビルドが表示され続ける場合は、最新版の配信後に同じ検証オリジンの `/match-test-update.html` をSafariで開きます。更新確認後に検証画面へ戻ります。Safariのサイトデータを消去する必要はありません。
- iPhone 8と15 Pro Maxの両方で、Safariから検証用URLを開き、画面の「試合記録の検証環境」、ビルド識別子、クラウド接続未設定の表示を確認します。ホーム画面に追加したら「AOBA LOG 検証用」を起動します。
- 「記録 → 詳細を入力」で「試合」を選び、メニューなしで、合成した「良かったこと」「改善したいこと」を入力します。同日に2件保存し、片方だけを編集・削除して、もう片方が残ることを確認します。
- ホーム画面版を一度オンラインで開いた後、アプリを閉じて開き直し、記録が残ることを確認します。次に機内モードで開き直し、記録の閲覧・追加・編集と、オンラインに戻した後も内容が維持されることを確認します。
- 「設定 → データ管理」から検証用JSONを「ファイル」に保存します。検証用アプリ内でそのファイルを選び、件数を確認して復元します。本番アカウントでログインしたり、本番のバックアップを復元したりする必要はありません。

## GitHub Pages での公開準備

1. 公開の承認後、GitHub のユーザー名とリポジトリ名を確定します。リポジトリの **Settings → Pages → Build and deployment → Source** で **GitHub Actions** を選びます。
2. クラウド同期を使う場合は **Settings → Secrets and variables → Actions → Variables** に `VITE_SUPABASE_URL` と `VITE_SUPABASE_PUBLISHABLE_KEY` を登録します。値はブラウザーに配信するビルドに含まれます。Supabase の管理用キーや `.env.local` は GitHub Actions に渡さないでください。
3. Supabase の **Authentication → URL Configuration** で、確定した HTTPS の公開 URL を **Site URL** と **Redirect URLs** に登録します。プロジェクトサイトの場合はリポジトリのサブパスと末尾の `/` を含めます。登録確認メールのリンクから同じ URL に戻れることを公開時に確認します。
4. 承認後、**Actions → Deploy AOBA TRAINING LOG to GitHub Pages → Run workflow** を手動で実行します。ワークフローは Pages から受け取ったサブパスでビルドし、テスト合格後に `dist` を配信します。

### iPhone のホーム画面に追加

1. Safari で HTTPS の公開 URL を開きます。
2. 共有メニューから「ホーム画面に追加」を選びます。「Webアプリとして開く」が表示される場合はオンにして追加します。
3. 「AOBA LOG」のアイコンから起動し、公開 URL のホームが開くことを確認します。オンラインで一度開いた後に、オフラインでも再起動できることを確認します。

ローカル開発版と公開版の保存領域は分かれます。公開前に既存の記録をJSONでバックアップし、同期済みのアカウントは公開版へのログイン後にクラウドの状態を確認してください。iOS 16 Safari ではファイル保存時に通常のダウンロードへ切り替わる場合があります。

## データモデル

### メニューの完全削除をローカルで検証

完全削除は公開版では無効です。検証時は専用ブラウザープロファイルと普段使わないループバックURL・ポートを使い、Supabase接続を無効化してから `VITE_ENABLE_LOCAL_MENU_DELETE=true` を指定して起動します。Supabaseが有効なビルドや公開URLでは、この指定をしても削除操作を利用できません。削除済みメニューを新たに持ち込むバックアップの復元にも同じ制限があります。

```powershell
$env:VITE_SUPABASE_URL = 'disabled'
$env:VITE_SUPABASE_PUBLISHABLE_KEY = 'disabled'
$env:VITE_ENABLE_LOCAL_MENU_DELETE = 'true'
pnpm.cmd dev --host 127.0.0.1 --port 5431 --strictPort
```

旧クライアントは、削除済みメニューを参照する記録や計画を読み込めないことがあります。本番で利用可能にする場合は、対応版の配信に加えて旧クライアントのアクセスを制御できる有効化手順を事前に決めてください。日付や利用端末の推測で有効にはなりません。

- 練習日は端末の暦日で保持します。登録・更新の時刻は ISO 8601 形式で保持します。
- 練習記録には個別 ID を割り当てます。同日の複数記録を扱えます。
- メニュー名、カテゴリ、単位は記録時点の値を保存する設計です。
- 週間目標は練習日数です。メニュー別の目標は実施量と単位の組で管理し、変更履歴を適用開始日付きで保持します。メニュー目標の集計期間は月曜から日曜で、変更後は今週の集計に反映されます。実績の単位が同じ記録を集計します。
- 休養日は予定として表現します。週次振り返りには週の月曜日の日付を使います。

## 開発段階

- Phase 1：データモデル、ホーム、下部ナビゲーション。振り返り欄は画面プレビューです。
- Phase 2：初期メニュー、記録の追加・編集・削除、目標と変更履歴、IndexedDB の基本保存。
- Phase 3：グラフ、予定と実績を確認するカレンダー、日次・週次振り返り、ポイント・レベル・バッジ。
- Phase 4：JSON バックアップと復元、オフライン対応、PWA。
- Phase 5：総合テスト、GitHub Pages ワークフローと公開手順、iPhone への追加手順。


## 日次目標とポイント

- 日次目標は設定画面のメニュー編集で入力します。当日に予定または実績があり、単位の合う日次目標があるメニューを評価します。実績のない予定メニューは0%、見送りは集計対象外です。集計対象がない日や休養日は「—」を表示します。
- 週間達成ポイントは月曜〜日曜に1回です。終了した週にはその週の日曜日時点の目標、今週には今日時点の目標を適用します。
- ポイントは練習日・記入済みの振り返り・週間目標の達成週・休養日の記録から計算します。予定を入力してもポイントは付きません。
- Lv. n の必要累計ポイントは 25 × (n − 1) × (n + 2) です。Lv.6 は 1000pt です。
- IndexedDB v3 への移行では既存データを保持して、見送り情報を追加する領域を作ります。予定を削除しても、見送りはカレンダーから確認・編集・解除できます。


## バックアップと復元（Phase 4A）

設定から「バックアップ・復元」を開き、JSONファイルを端末に保存できます。保存ダイアログを利用できる環境では、書き込み完了後に成功を表示します。ダウンロードの場合はブラウザの保存先でファイルを確認してください。

復元するファイルを選ぶと、作成日時と現在・復元後の件数が表示されます。内容を確認して「全データを置き換えて復元」を押した場合にだけ、端末内データが置き換わります。

バックアップは形式バージョン1で、アプリ識別子、作成日時、データ形式バージョン（現在は3）、既存の保存データ本体を含みます。ポイント・レベル・バッジは復元したデータから再計算されます。



## Supabase 認証とクラウド保存基盤（Phase 4B）

専用の Supabase プロジェクトを用意します。既存の AOBA BASEBALL LAB とプロジェクトを共有しないでください。設定を行わなくてもローカル機能を使えます。

1. Supabase の SQL Editor で、新規プロジェクトに [スキーマの SQL](supabase/migrations/202611180001_training_log_snapshots.sql) の全文を実行します。先頭は `-- AOBA TRAINING LOG only.` です。
2. Authentication で Email プロバイダーを有効にします。新規アカウントの自己登録を使う場合はサインアップを有効にします。アカウントを事前管理する場合は事前に用意したアカウントで利用します。
3. メール確認を使う場合は Email の Confirm email を有効にし、Confirm signup テンプレートに既定の確認リンク `{{ .ConfirmationURL }}` を残します。Authentication の URL Configuration で Site URL と Redirect URLs に、実際に開くアプリのURLを登録します（例 `http://127.0.0.1:5173/`）。GitHub Pagesを利用する場合はリポジトリのサブパスまで含めます。
4. Supabase 標準のメール送信を使います。既定SMTPが確認メールを送れる宛先は、そのプロジェクトが所属する組織のチームメンバーです。Supabase管理画面のメールアドレスをアプリ登録に使えます。
5. ファイル `.env.example` を `.env.local` にコピーし、専用プロジェクトの HTTPS URL と `sb_publishable_` で始まる Publishable key を設定して、開発サーバーを再起動します。秘密鍵や service_role キーを Vite の変数に入れないでください。
6. 「設定 → クラウドアカウント → 新規登録」から、アプリ専用のパスワードを設定します。確認が必要な場合はメール内のリンクを開きます。再読み込み後もログイン状態は保持され、ログアウトは現在のセッションが対象です。

ログインしていないときは従来の端末内データで記録できます。ログインするとプロジェクトとユーザーIDに対応する端末内データを開き、同じアカウントのクラウドと同期します。

### Phase 4C の同期動作

- 空の端末は同じアカウントのクラウドデータを取得します。従来の端末内データがある場合、初回同期で使用する内容を選びます。未ログイン時の元データは端末に残ります。
- 記録・編集・削除は最初にアカウント別のIndexedDBに保存します。送信世代と送信中の内容も保持し、接続回復やアプリ再開時に再確認します。応答の途切れでクラウド側だけ保存された場合は、再取得した内容を照合して確認します。
- 競合時は自動で統合せず、設定の「クラウドアカウント」で端末とクラウドの件数を比較して選択します。使用しなかったデータは端末内に退避し、JSONとして保存できます。
- ログアウト後は未ログイン時のデータを表示します。アカウント内のデータは端末に残り、同じアカウントで再ログインすると表示されます。
- ビルド版では、オンラインで一度開いて静的ファイルが保存された後、オフラインでも画面を開けます。クラウド送受信はアプリを開いている間に行います。JSONの書き出し・復元は、そのとき表示しているデータに対して行われます。ログイン済みの場合、JSON復元も同期対象です。


### スナップショットのrevision付き更新

初回登録は本人の行を `INSERT` します。既存行の更新は認証済みセッションから `training_log_update_snapshot(expected_revision, new_data)` を呼びます。照合に成功した場合は `status = updated` と新しいrevisionが返ります。revisionの不一致や本人の行が存在しない場合は `status = conflict` が返り、更新されません。競合時は最新の行を読み直して比較します。

初版のSQLを適用済みの場合は、ファイルの `-- Protect this write path` から末尾までを、先頭に `begin;` を付けて適用します。この変更では既存のスナップショットを編集しません。




### クイック記録（Phase 4D）

ホームの「今日のクイック記録」で、プラス・マイナスを短く押すと1、約500ms以上押して離すと10ずつ変わります。名前または数値をタップすると実施量の合計を入力できます。キーボードでは通常のボタン操作で1、Shift＋EnterまたはShift＋Spaceで10ずつ変更できます。

今日の同じ単位の実績合計と日次目標を表示します。クイック入力は専用の実績だけを増減します。詳細入力した記録を減らしたり取り消したりする場合は、練習履歴から操作してください。

ホームの「直近7日間」の日付を押すと、予定区分だけを編集できます。保存するまで変更は反映されません。予定を解除しても実績は残ります。予定メニューや見送りの詳細はカレンダーから編集できます。



### 曜日別・月次計画（Phase 4E）

「設定 → 練習計画の管理」で、毎日、曜日別、条件付き・任意を指定できます。数量を記録する種目は既存の記録メニューを選びます。セットの内訳や時間を確認しながら行う種目は、計画の説明だけを表示することもできます。

- ホームでは今日の曜日・毎日の種目・日付別の予定メニューを表示します。条件付きの種目は本人が今日の計画に追加できます。その他の記録メニューは一覧を開いて入力できます。
- 「翌月版を作る」は今の種目をコピーし、翌月1日を初期値にします。適用開始日は今日以降で変更できます。各版は履歴に残り、過去の日付には当時の版を使います。
- 「Excel初期取り込み」では指定のシートのセルを読み、列と行範囲を指定した後、候補を1件ずつ確認します。複合目標、数式、解釈できない曜日、既存の記録メニューと対応しない項目は要確認です。時間セルは確認できる範囲で表示値・元値・表示形式を確認できます。
- 確定前にJSONバックアップを保存できます。取り込みの重複判定には対象シートの内容から計算した識別子を使います。
- 計画および条件付きの追加は、既存の保存データに任意の項目として含まれます。IndexedDBの移行とSupabaseのSQL変更は不要です。


### version6 の初回取り込み（Phase 4E.1）

「設定 → 練習計画の管理 → Excel初期取り込み」で元のブックを開きます。A1の表題とB〜H列の曜日、結合セル、筋トレ内訳を確認し、対応する形式では列の指定を省いて候補を表示します。確認した種目だけを確定できます。毎月の変更はアプリ内で適用開始日を指定して保存します。

数量種目は目標と同じ単位で記録します。セット種目の1セット当たりの内容は種目名に表示します。完了チェックは計画の完了として保存し、既存の練習実績数量やポイントに換算しません。記録単位や名称を変更して新しい版を保存した場合、既存の実績や過去の版は保存時の状態を保持します。
